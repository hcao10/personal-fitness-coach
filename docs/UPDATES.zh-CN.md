## 2026-08-09

### F7 阶段 7（L7-0/1/2）：LLM 按 locale 的地基、提示词模块化、语言溯源

**采用的架构，一句话**：人审过的内容可以多语言；模型写的内容单语言 + 记录创作语言。

**L7-0 类型地基。** 六处调用点写着 `x.locale === "en" ? "en" : "zh"`。这不是类型收窄，是把「世界上只有两种语言」编译进了调用点：加第三种语言时它到处都能通过类型检查，然后把中文发给每一个选了那种语言的人。现在统一走 `toLocale()`——存储列、请求体、客户端选项都是同一个入口，降级只发生一次且是有意的。同一个假设在类型层也写了十几遍（coach-core 的 `{ zh: string; en: string }` 字面量），收敛为一个 `Localized<T>` 别名；coach-core 用本地定义而非 import `packages/i18n`，因为它作为零依赖包独立发布，这一点必须保持为真。`MealCandidate` 此前有 worker / 网页 / Expo 三份互不相干的定义，可以各自漂移而编译器不会察觉，现在归一到 api-contracts。

**L7-1 提示词模块化。** 三段系统提示以单行字符串字面量的形式住在 `llm.ts` 里，其中一段用内联三元决定输出语言。这个形状对第三种语言的唯一答案是更长的三元，对「是哪版提示生成了这份糟糕计划」则没有答案。`worker/prompts/` 把每段提示拆成：与语言无关的任务契约、指明目标语言的输出指令、语域说明、按任务裁剪的术语表。**指令层对所有语言一律英文**是刻意的——翻译整份提示意味着每条安全规则存在 N 份副本，修好一份就等于只修好了一份；测试断言各 locale 的契约段逐字节相同。安全文本由 `PAIN_THRESHOLD` 与 `INTENSITY_RAISING_ACTIONS` **插值**生成而非重新抄写：提示里写着服务端并不执行的阈值，等于在教模型跟代码唱反调。这种耦合正是提示词该留在仓库里、与动作 ID 枚举一起版本化的理由，而不是放进一个可以被绕过代码改掉的外部提示注册中心。`PROMPT_VERSION` 与全部提示的 FNV-1a 指纹互相钉死，改文案不改版本号会让 CI 失败。

**顺带修掉一个真实缺陷**：周复盘用一句写死的中文向模型索要解释（`"请用简洁自然的语言解释这份周度复盘…"`），所以英文用户的复盘是在中文指令下生成的，回复用什么语言全看模型自己猜。

**L7-2 语言溯源（只观测）。** 新增按脚本比例的语言检测（`packages/domain/src/language.ts`）。模型也被要求回显自己用的语言，但那是**自述而非证据**——一个无视了输出指令的模型，同样会照抄它被告知的 locale；脚本比例是从产出文本本身量出来的，因此两者恰好在出问题时才会不一致。阈值是实测过的：一句含 "RIR" 的 20 字中文是 0.87 汉字比，一句含「深蹲」的 100 字母英文是 0.02。**检测器拒绝猜共用文字的语言**——区分英语和西班牙语需要 n-gram 模型，猜错比不答更糟，因为它会把正确的西语报成「漂移」，直到所有人学会无视这个告警。写测试时发现并修掉了一个真实漏洞：未登记文字的 locale 原本会被当作「自成一种独有文字」，于是检测器会自信地报出另一种语言。

迁移 0012 给 `generation_runs` 加 `locale` / `content_locale` / `prompt_version`；admin 面板新增漂移表。**仅观测，不重试不拦截**：在知道漂移率之前就重试，等于花钱重跑本来没问题的生成。面板把「未检出」与「偏差」分列——文本太短无法判断是未知，不是出错，把两者合并会凭空造出一个失败率。`training_plan` 与 `meal_vision` 的输出目前仍是双语的，所以它们只记请求语言，`content_locale` 留空：一份同时含两种语言的产出，「这是什么语言」本来就没有答案可记。

### F7 阶段 7（L7-3）：coach_chat 单语言化——证据优先于自述

coach_chat 的 schema 增加 `content_locale`：模型回报自己用了什么语言。但服务端**不采信它**——`contentLocale` 解析顺序是 `检测 ?? 自述 ?? 请求`。理由很直接：一个无视了输出指令的模型，同样会照抄它被告知的 locale，信自述等于永远发现不了这个字段本来要抓的失败。自述只在文本短到无法测量时才被用上，而两者不一致本身（`localeClaimMismatch`）会写进 `coach_evaluation_runs`——自报与实际产出打架的模型，两件事上都不可信。

迁移 0013 给 `coach_messages` 加 `content_locale`。**旧消息留 NULL**：它们的语言当初就没记录过，事后猜一个填进去，等于把编造的溯源和测量的溯源放进同一列。用户消息的语言也测量而非按界面语言假定——界面设成英文的人照样用中文提问。

这一列有实际用途，因为**切换语言时绝不机器翻译已存内容**，所以一段对话里合法地存在多种语言的消息，客户端和模型都需要知道哪条是哪种，而不是靠猜。

**顺带修掉**：紧急分诊回复的 limitations 写死中文「这不是医疗诊断。」，英文用户收到的是中文免责声明。改为按 locale 渲染（`medicalDisclaimer()`，与安全指引同处一室，同样按语言完整性受测）。注意这条与模型产出的规则相反且理由相反：它是人工审校过的确定性产品文案，所以按**读者**语言渲染；模型写的内容按**创作时**语言冻结。

**原设计里的「流式先缓冲后嗅探」没有采纳**，理由见 HARDENING_PLAN 对应小节——用真实首字延迟换一个当前不会执行的策略，不划算。

### F7 阶段 7（L7-4）：meal_vision 单语言化

`name_zh`/`name_en` 换成 `name`（按输出语言）+ `search_term_en`，`content_locale` 放在**响应级**而非每个候选上——一次调用只产出一种语言，放在候选上等于暗示存在不可能发生的混排，还得每条填同一个值。

`search_term_en` 需要解释一下它**不是**双语输出的化名：USDA 与 Open Food Facts 的索引是英文的，`searchFoods()` 用中文菜名去匹配会显著变差。它是**查库用的机器键，永不展示**，语言由被查的数据库决定而不是由读者决定——这跟「给读者两种语言让他自己挑」是两回事。提示词里也是这么讲的：优先给数据库常用名（"white rice, cooked"）而不是字面直译。

候选的语言检测在**所有展示名拼接后**做：单条菜名太短测不出来，拼在一起就是全部用户可见文本。`meal_analysis_runs.result_json` 是只写不读的审计记录，所以历史行保留旧结构不需要容错读取；`created_at` 本身就标注了它属于哪个时代。

### F7 阶段 5：其余产品页接入词表（含对抗式复核与修复）

**先建地基**：语言此前只存在于首页组件的 `useState` 里。这才是其余 8 个页面至今全是硬编码中文的**真正原因**——翻译函数没有来源，嵌套组件（比如产品外壳）除了层层传 prop 之外无路可走。`LocaleProvider` 在 `layout.tsx` 用服务端解析出的 locale 包住整棵树，任何客户端组件 `useT()` 即可。**没有 provider 时抛错而不是回退默认**：静默回退渲染出的是中文，正是这件事要消灭的失败模式。

9 个命名空间并行迁移后做了**对抗式复核**，抓出 4 个 blocker + 12 个 major。它们不是逐页问题，是三个系统性根因：

**根因一：`localizeApiError` 的解析顺序本身是错的。** 原为 `词表 → body.message → 兜底`，而 `body.message` 是用一种语言写死的。于是只要某个 code 不在词表里，英文用户拿到的就是中文，页面自己的英文兜底成了死代码——又因为服务端**总是**发 `message`，这等于**五个页面上的每一个报错**。改为 `词表 → 调用方兜底`，服务端原文只留给读那门语言的人；并补了约 50 个用户真能撞到的错误码（webhook 与令牌类的故意不收，它们到不了屏幕，收进来只会淹没真正会出现的）。

**根因二：一条安全指令在用读者没选的语言显示。** 周复盘直接渲染 `packages/domain` 的中文散文，deload 分支里有一条是「持续疼痛时停止相关动作并咨询专业人员」。该分支触发条件是疼痛 ≥ 4/10——和教练安全门同一阈值，也就是说**最需要读到它的人恰好是收到看不懂语言的那个人**。现在引擎照旧判断，文字按它本来就返回的机器码 `kind` 从词表取；`kind` 出现前存的旧复盘，中文读者看原文，其他人看诚实占位。

**根因三：整页内容以 `.zh` 硬读。** 今日页把整场训练（日标题、重点、每个动作的名称/目标/要点/进阶，以及 aria-label、图片 alt、两个 /coach 深链）都读 `.zh`。全部改走 `pick()` 并配真实兜底。账户页的 hero 此前对「有计划但没写重点」的人回退到**没有计划**那句文案，对旧计划则渲染出空 `<h1>`。

**顺带修掉的真实缺陷**：账户页日期格式写死 `zh-CN`，计划日期、身体记录、账单周期对所有人都渲染中文；`MessageKey` 只支持两层而迁移指引却要求分组，分组对象能通过类型检查、运行时渲染成 `[object Object]`（类型与 translator 现在都支持任意深度）；英文复数——中文只有一个复数类别，所以一次写成的文案在英文里是 "1 exercises"、"1 plans left"、"1 sessions in total"（最后一条恰好发给第一周的用户，也就是习惯卡片的目标受众），现在由 `t.plural()` 经 Intl.PluralRules 选形；`beginCmineLogin` 的 locale 被加成了**可选参数而没有任何调用方传**——同一个 bug 换了个更宽的签名，改为必填后编译器一次点出全部 13 处。

**明确没做**：`app/admin`（自己人用的运营台）、`app/privacy` 与 `app/disclaimer`（法律文本，需要有资质的人审，不是 UI 字符串迁移）。今日页的 check-in 建议与每日简报仍是服务端写死的中文且无 locale 参数，归入阶段 9。

新增两条守卫：非中文词表**混入汉字**的检测（值与中文不完全相同、旧的 passthrough 检测抓不到、但里面还留着中文），以及每个产品页命名空间**必须非空**（防止某页被悄悄跳过：命名空间存在、能编译、但是空的）。

### F7 阶段 7（L7-5）：training_plan 单语言化——先分清哪些是「人写的」

这一步的关键不是把双语字段改成单语言，而是先分清计划里**哪些文字是人审过的、哪些是模型现写的**：

- **人审过的**：动作名/目标/要点（来自审核过的动作池）、`stopConditions`（我们自己写的双语安全提示）、以及**日程标题与重点**——现在也归入这一类。
- **模型写的**：`summary` / `planRationale` / `coachNotes` / `dietGuidance`。这四项变成单语言 + `contentLocale`。

**日程标题不再由模型写。** 原先每天要模型产出 `title_zh`/`title_en`/`focus_zh`/`focus_en` 四个字段，一份计划七天就是 28 个模型撰写的字段——而这些文字完全是公式化的，且两个语言版本是否对得上没人能验证。改为 `describeSession()`：按模型实际选中的动作模式派生，确定性、可单测，并且因为标签是**写好审过的**所以天然多语言。顺带省下一批 token，也少了一个语言漂移面。

**旧计划不迁移**，`readPlanInsights()` 同时读两种结构。理由前面写过：`users.locale` 可变，数据库没有诚实的办法判断当初哪一份是权威版本。改成联合类型后编译器一次性指出了全部 6 个读取点——其中 `app/account/account-dashboard.tsx` 写死了 `.summary.zh`，英文用户的计划历史一直显示中文摘要。

**缓存键**从 `sha256(profile)` 改为 `sha256({profile, locale, promptVersion})`，与写入方在同一次部署上线。不改的话，用户切到英文会拿到几分钟前缓存的中文计划，而提示词修复要等缓存过期才生效。

**schema 的 maxLength 统一取原英文值**：按中文字数调的上限会把其他语言截在句子中间。

### F7 阶段 7（L7-7）：契约评测——顺带发现验收逻辑零覆盖

每个任务 × 每个 locale 一份预置模型响应，跑真实的解析与验收路径，无需 key、无需网络，CI 里就能跑。**它测不出计划好不好**——那需要真实 profile 的在线生成；它锁的是 schema 与领域模型之间的契约，也就是改提示词或改 schema 时最容易悄悄崩掉的地方。

写的过程中发现了更值得补的东西：`applyAiPlan` 里那道「模型建议 → 产品处方」的验收（未知动作 ID、用户没承诺的训练日、用户没有的器械、被篡改的热量与宏量）**此前一个测试都没有**。现在每一条都有，包括「模型把训练日整周镜像挪位」这种同样天数但换了日子的情况。

### F7 阶段 8：按语言的安全分诊（加任何新语言前的硬阻塞）

原先的安全门是一条正则：中文关键词 + 三个**必须精确匹配**的英文短语（`sharp chest pain` / `faint` / `cannot bear weight`）。实际后果是——说 "I have chest pain" 不触发（缺 sharp），说 "I can't breathe" 不触发，任何非中英语言完全不可见。

- **模式注册表按语言组织**（`packages/domain/src/safety.ts`），但**每条消息都用全部语言的模式筛查**，不按用户界面语言过滤。理由很实际：界面设成英文的人照样会打「胸痛」，反之亦然；按 locale 过滤恰恰会制造这次重写要消除的盲区。
- **语言无关的数值形式单独注册**（`8/10`、`7 分`），因此**尚未翻译的语言也能读出已陈述的疼痛分数**——测试里那条 `dolor 8/10 en la rodilla` 现在会被判为 caution。
- **严重程度分级**，这是对上一轮审计意见的正面回应：红旗症状（胸痛/晕厥/无法承重/麻木/骨折声）短路，不经过模型，因为唯一正确的回答就是停止并就医；而**疼痛分数不再短路**——一个说「膝盖 6/10 疼，今天该练什么」的人应该得到真实建议（换动作），拒绝回答只会把他推去自己硬扛。caution 级别照常调用教练，但追加安全指引并**扣留全部提升强度的动作提案**。
- 英文红旗词表从 3 条扩到 8 组，覆盖 chest pain/pressure、faint/pass out/dizzy、can't breathe、can't bear weight、numbness/tingling、dislocation/fracture/heard a pop、palpitations、worsening pain；疼痛分数支持 `pain is 7`、`8/10`、`seven out of ten` 等写法，并取消息中**最高**的一个分数判定。
- **上线闸门测试**：`tests/safety-rules.test.mjs` 对 `SHIPPABLE_LOCALES` 中的**每一种语言**断言其必备急症短语被识别、疼痛分数可读、日常训练用语不误报。**一种语言在这三项通过之前无法上线**——这就是让「我们支持 X 语」这句话有实际含义的机制。
- 另有一条测试**明确记录了关键词层的已知盲区**（完全改写的表达仍然逃逸），把这个限制固化成可见事实，说明第二层模型判定为何必须存在。
- 开源仓库同步。

### F7 多语言阶段一：基础设施、首页迁移、语言真正可达

**一处更正**：此前我说「9 种语言是假的」并不准确。逐条计数核实后：`data/exercises.json` 确实含 **en/it/tr/es/ru/zh/hi/pl/ko 九种语言**，1324 条记录每条都有全部 9 种、覆盖率 100%、每种语言 7,710 个逐步对齐的步骤，且**没有一条是复制英文充数**。假的是**界面**——选择器提供 9 项而其中 7 项选了毫无变化。删掉那个选择器是对的，但当时把数据集也一并说成假的，是错的。这个平行语料是真实资产，也显著降低了后续加语言的成本。

**更大的发现**：英文其实也从未真正可用。`users.locale` 建号时写死 `'zh'` 且全仓库无一处更新，21 个界面里只有首页是语言感知的，而它的语言选择是组件本地 state，翻页即丢。所以 100% 的用户拿到中文 LLM 回复、中文推送、中文教练文案——**选择器一直是个摆设**。

- **基础设施**：`packages/i18n` 成为 Web、Worker、Expo 三个运行时共用的唯一来源。不引入 i18n 库——它们只解决 Web 那一份，且都会用运行时缺键回退替换掉本项目赖以生存的编译期完整性保证。`LOCALES`（能编译）与 `SHIPPABLE_LOCALES`（可展示）分离，语言选择器只读后者；中文目录是类型模板，其他语言 `satisfies Messages`，缺键多键都无法编译。
- **首页全量迁移**：112 处内联三元 + 74 键遗留 copy 表并入统一词表。两次迁移都由**可重跑、已入库的 codemod** 完成而非手工搬运——转写 186 条双语字符串正是引入静默错误的典型场景。codemod 正确跳过了唯一一处 BCP-47 语言标签（那是数据不是文案），其碰撞检测还抓出一个真实冲突：导航链接和段落标题都想叫 `nutrition`。
- **语言真正可达**：cookie + `users.locale` + Accept-Language 三级解析，服务端渲染时即确定，因此 `<html lang>`、`dir` 与页面元数据从第一个字节就正确（客户端纠正会让读屏在首屏念错语言）。新增 `PUT /api/v1/me/locale` 写入 `users.locale`——这是让 LLM 回复、推送和周教练信跟随用户选择的前提，它们都在没有浏览器的环境里运行。
- **服务端错误本地化**：`errorJson` 的第一个参数一直是稳定 code，所以本地化只是一次已存在键的查表。**翻译放在客户端**：Worker isolate 服务并发请求，任何存在服务端的「当前请求语言」都是竞态；这一点在实现中途发现并改正。
- **测试**：`tests/i18n.test.mjs` 覆盖类型表达不了的部分——键集一致、无空值、占位符集跨语言一致、非中文目录不是中文的原样复制、中文目录里没有漏译的英文句子。

### F6 移动端拍照识别与条码扫描

- **先修了一个会让整个功能无法工作的传输层缺陷**：`apps/mobile/src/api.ts` 在有 body 时无条件设置 `content-type: application/json`，这会破坏 multipart 边界——在此之前任何文件上传都发不出去。现在 `FormData` 保留自己的 content-type。
- **新增 `apps/mobile/src/meals.ts`**：上传前本地压缩（1600px / JPEG / q0.75）。这不是优化而是必需——iOS 默认返回 HEIC，既过不了服务端的 MIME 检查，也过不了转换后 2MB 的上限；在客户端解决，用户就不会等半天才收到失败。
- **拍照流程**：拍照或从相册选 → 上传 → 识别 → **候选确认屏** → 记录。确认屏是这个功能的诚实性边界，一步都不能省：显示每个候选的置信度与不确定性说明，克数输入框预填估算中点但**必须由用户确认**，没有匹配到食物库条目的候选会明确告知「无法计算热量」而不是猜一个数。这与网页版共用同一批端点，服务端零改动。
- **条码扫描**：`expo-camera` 内置扫码（EAN/UPC/Code128），用 ref 锁阻止 RN 相机对同一条码的连续重复触发；另提供手动输入条码的降级路径。
- **权限**：iOS/Android 相机与相册权限文案写明具体用途（Apple 会专门审查这一点），并且**拒绝后不走死路**——给出前往系统设置的入口，同时提示可改用扫码或搜索。
- **额度前置可见**：进入拍照前显示本周期剩余识别次数，额度用尽时直接说明可用积分兑换或升级，而不是让用户拍完才碰壁。
- **删除了那句「拍照与扫码请使用网页版（App 版开发中）」**——承诺兑现了才删。

### F8 无障碍

- **模态焦点管理**：新增可复用的 `app/lib/use-dialog.ts`——打开时焦点进入对话框、Tab 在内部循环、Escape 关闭、关闭后焦点回到触发元素。此前五个模态只有 `aria-modal` 属性，而它本身不做任何这些事：键盘用户按 Tab 会静默走到背后的页面里。已接入首页三个模态（安全同意、登录、广告）、动作目录详情与今日动作媒体。安全同意模态传 `null` 作为关闭回调——它必须被回答而不是被绕过，因此 Escape 不生效，但焦点仍被限制在内。
- **控件语义**：单选式按钮组（训练路径、性别、目标）此前只用 `class="active"` 表达选中，对读屏完全不可见，现改为 `role="radiogroup"` + `role="radio"` + `aria-checked`；日程 `role="tablist"` 补上对应的 `tabpanel`、`aria-controls` 与路线图式 `tabIndex`（此前 tab 不控制任何东西，关系是断的）；7 个滑块的数值从可访问名中移出并改用 `aria-valuetext`（此前读屏把「精力 3/5」整体当作标签朗读）；装饰性字形加 `aria-hidden`。
- **对比度**：逐个按元素**实际所在背景**测算而非套用估计值，修正 5 处未达 WCAG AA 4.5:1 的muted 文本（最差的 `.week-strip div` 仅 3.27:1），沿各自色相取最小达标值（均升至 4.54:1）。顺带纠正一处审计误报：`.preview-header` 的 `#a2a59e` 在深色底上实测 7.22:1，本来就合格，未改动。
- **字号可缩放**：`app/globals.css` 的 448 处字号全部由 px 转为 rem。默认 16px 根字号下渲染像素级不变，但**用户放大字号终于生效**——此前整份样式表只用 px，意味着浏览器字号设置被完全忽略，这才是真正的无障碍失败。转换由 `scripts/normalize-css-a11y.mjs` 完成，可重跑可审计。
- **移交给你的设计决策**：11px 以下的字号共 350 处（含 6px×1、7px×14、8px×136）。是否抬高这个下限属于视觉设计判断，需要你在真机上确认，代码层面不宜替你决定；已记入 HARDENING_PLAN。

### 配置审计发现的 5 个缺陷修复（含对抗式复核后的二次修正）

先修了 5 个缺陷，然后派独立检查者逐条尝试推翻"已修复"。**5 条全部被推翻**，以下是复核后的最终状态：

- **AI 预算对饭菜识别不再是瞎的，但真正的洞是别处**。原修复只在整条调用成功时记账；复核指出 `/api/v1/meals/analyze` 是唯一没有限流的 AI 端点，且失败时退还配额——一张必然识别失败的照片可以无限重试，既真实计费又永远不累计预算。已补：该端点加限流（12 次/10 分钟）；成本记录移到 `searchFoods` **之前**（食物查询抛错会连带丢掉已计费的成本）；`estimatedCost` 在供应商不返回 token 用量时给出非零下限（此前注释宣称的"保守高估"对这种情况恰恰失效）；失败路径**不再**写 `generation_runs`——预算拦截与无可用路由从未接触供应商，把它们记成 AI 失败会让管理台的成功率在预算防线正常工作时反而下跌。

- **`IMAGES` 绑定在整个仓库里根本不存在**——这是最严重的一条。`.openai/hosting.json`、`vite.config.ts` 与生成的 `dist/server/wrangler.json` 都没有声明它，意味着**饭菜拍照功能在任何能构建出的环境里都从未工作过**；我加的守卫只是把误导性的 400 换成了诚实的 503。已在 `vite.config.ts` 真正声明该绑定，并让 `/api/health` 的 `vision` 要求视觉路由 + `R2` + `IMAGES` 三者齐备，另加 `imageTransform` 位与管理台对应模块行。
